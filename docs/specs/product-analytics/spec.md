# Spec: 사용자 행동과 이탈 분석

> Status: approved — 2026-11-08 사용자 요청으로 브랜치 분리·이벤트 계측 구현 승인.
> 작성일: 2026-11-08
> 승인된 지표·이벤트 계약 v1. 앱 계측의 로컬 구현·빌드 검증을 완료했으며 운영 수집은 아직 시작하지 않았다.

## 배경 / 문제

사용자가 뉴독의 어느 화면·기능을 자주 쓰고, 어떤 뉴스레터를 발견·구독 시도·열람·저장하며,
어디서 멈추고 다시 돌아오는지 판단할 기준이 필요하다.
Firebase Analytics SDK 연결은 있으나 Swift 소스의 명시적 행동 이벤트는 확인하지 못했다.
실제 콘솔 수집·개발/상용 데이터 분리 여부는 미확인이다.

현재 흐름에서는 다음 사실을 구분해야 한다.

- Apple·Kakao 기존 회원 로그인, 신규 가입 필요, 사용자 취소, 게스트 진입.
- 계정 생성 성공, 이후 관심사 저장, 추천받기 건너뛰기, 메인 표시.
- 홈의 구독 없음, 선택한 날짜에 기사 없음, 요청 실패.
- 기사 선택, API 응답, WebView 본문 표시, 활성 상태의 유효 열람.
- 뉴스레터 상세와 가입 추천 양쪽의 구독 진입, 외부 페이지 표시·복귀, 실제 구독 완료.

## 목표 (Goals)

- 첫 방문 → 진입 → 발견 → 열람 → 재방문에서 개선할 구간을 찾는다.
- 화면의 도달·표시 빈도와 검색·읽기·북마크·하이라이트·구독 시도의 실제 기능 이용을 구분한다.
- 뉴스레터별 상세 관심·독자 수·독자당 열람·구독 시도·저장 활용을 비교한다.
- 지표의 분모·기간·성공·중복 기준을 고정한다.
- 각 필드가 현재 지표나 그 지표의 오류 진단에 쓰이게 한다.
- 새 기능은 필요한 이벤트·타입·보고서 계약을 추가해 확장한다.

## 비목표 (Non-goals)

- 앱 구조 전환 평가, 화면·가입·구독 동작 변경, SDK 교체.
- 광고 기여도·매출 분석, 사용자 원문·세션 녹화, 모든 버튼·HTTP·스크롤 수집.
- 이벤트만으로 이탈의 심리적 이유나 인과관계 확정.
- 자체 전송 큐·범용 provider 체인·영구 분석 상태·별도 Analytics 모듈 구축.
- 첫 버전에서 정확한 홈 회복 경로 추적, 요청별 재시도 분석, 계정 통합·실제 구독 완료 분석.
- 이번 문서 작업에서 앱 구현·외부 설정·BigQuery 연결·배포 수행.

## 유저 스토리

- 제품 담당자는 가입 이전과 첫 열람 이전 중 어느 구간에서 멈추는지 구분한다.
- 제품 담당자는 빈 홈의 종류와 안내 선택 여부를 보고 안내·콘텐츠 공급을 조사한다.
- 제품 담당자는 진입 경로별 열람 전환과 다음 주 읽기 유지율을 비교한다.
- 개발자는 사용자 작업 오류와 잘못된 중복 계측 때문에 지표가 왜곡되는지 검증한다.
- 기능 개발자는 현재 측정 계약을 깨지 않고 필요한 새 사실만 추가한다.

## 범위와 최소 수집 기준

[metrics.md](metrics.md)는 지표 정의, [events.md](events.md)는 이벤트·파라미터의 기준이다.

| 단계 | 범위 | 결과 |
|---|---|---|
| P0 | 화면·단계, 인증·가입, 홈 상태·안내 선택, 콘텐츠 선택, 기사 표시·열람·북마크·하이라이트, 작업 실패 | 화면·읽기·저장 이용과 첫 경험 병목 |
| P1 | 검색 시작·결과, 뉴스레터 상세, 구독 시작·페이지 표시·복귀 | 검색 이용과 뉴스레터별 발견·구독 관심 |
| 분석 준비 후 | 원시 데이터의 기간·조회·세션 집계 | 문서의 정확한 산식. GA4 개요와 구분 |
| 필요 확인 후 | 신규 구독 완료, 홈 안내 이후 실제 회복, 반복 요청 분석 | 제품 질문·데이터 근거를 먼저 정하고 별도 계약 추가 |

수동 이벤트의 공통 필드는 5개다. 추가 ID 6종은 해당 지표의 흐름에만 사용한다.
모든 이벤트의 고유 ID·전역 화면 방문 ID·독립된 검색/로드/선택 ID·회복 전파 ID는 초기 구현에서 제외한다.
SDK 사용자·세션·앱 버전을 재사용한다. 중복 노출 이벤트는 합친다.
이번 이용 분석 요구에는 기존 이벤트를 재사용하고 검색 시작·북마크 변경·하이라이트 적용만 보완한다.
새 공통 필드·UUID는 추가하지 않는다. 공개 뉴스레터 이름은 ID 기반 집계의 선택적 표시값이다.

## 요구사항

### R1. 제품 지표

- 대표 지표 후보는 주간 유효 열람 사용자 수, 지속 사용 지표는 다음 주 읽기 유지율이다.
- 초기 유효 열람은 본문 표시 후 활성·가시 시간 누적 30초다. 완독 판정은 아니다.
- 가입 완료와 프로필 완료·건너뛰기, 구독 클릭과 실제 완료를 분리한다.
- 초기 홈 지표는 안내 선택률이다. 선택 후 성공적인 열람·구독으로 회복됐다는 뜻으로 표시하지 않는다.
- 화면 도달은 실제 기능 사용과 다르다. 화면에는 도달 사용자·표시 전환, 기능에는 정의된 실제 행동을 집계한다.
- 뉴스레터 순위는 조회·유효 독자·독자당 열람·구독 시도·저장을 각각 제공한다. 하나의 인기 점수로 합치지 않는다.
- 브랜드 소개 조회와 기사 본문 조회를 구분하고 본문 조회 사용자·30초 유효 독자를 함께 표시한다. 짧은 뉴스레터의 사용을 0으로 해석하지 않는다.
- 발행량·노출량 차이를 고려하며 절대 열람량을 콘텐츠 품질이나 노출 대비 선호율로 부르지 않는다.
- 목표 비율은 기준선·모수·관찰 기간을 확보한 뒤 정한다.

### R2. 측정 품질

- 진행 중 이탈은 정의한 기간 안에 다음 행동이 관측되지 않은 경우다. 종료 이벤트를 필수로 삼지 않는다.
- 계측 이전 행동 부재·미성숙 코호트·누락을 0이나 이탈로 바꾸지 않는다.
- 성공은 현재 유효한 결과가 반영된 시점, 노출은 실제 보인 시점이다. 취소·오래된 응답을 실패로 기록하지 않는다.
- 개발·테스트 트래픽을 운영 KPI와 분리한다. DebugView만으로 제외가 보장된다고 가정하지 않는다.
- 수집 중복은 지표의 사용자·세션·조회 단위와 로컬 발생 제어로 처리한다. 정확히 한 번 전달을 보장한다고 표현하지 않는다.
- 초기 사용자 단위는 앱 인스턴스다. 사람·계정·설치 다운로드 수와 혼합하지 않는다.

### R3. 필요한 필드와 확장

- 이벤트·필드마다 사용하는 지표 또는 현재 진단 목적을 명시한다. 소비자가 없으면 초기 수집에 넣지 않는다.
- 현재 값은 enum·명시적 모델로 표현한다. 임의 딕셔너리·미리 만든 확장 필드·기능별 설정 플래그를 두지 않는다.
- 새 사실이 필요할 때 지표 → 이벤트 → 타입·변환·검증 → 보고서 순으로 추가한다.
- 이벤트 계약과 지표 정의는 별도로 버전 관리한다. 의미·기간이 다른 값을 같은 시계열로 이어 붙이지 않는다.
- 원시 데이터가 준비되지 않았어도 현재 지표에 필요한 조회 연결 키는 해당 이벤트에만 수집한다. 미래 분석용 ID는 미리 추가하지 않는다.

이 기준을 적용한 선택·제외 근거와 추후 추가 조건은 [plan.md](plan.md)의 최소 수집·확장성 판단 기록에 남긴다.
확장성을 이유로 사용처 없는 필드·대기 이벤트를 구현하지 않으며, 새 지표의 수집 시작 이전 정보는 소급 복구할 수 있다고 약속하지 않는다.

### R4. 데이터와 동작

- 이메일·닉네임·생년·성별·토큰·본문·선택 문장·검색어 원문·전체 URL을 전송하지 않는다.
- 콘텐츠는 검증된 내부 ID, 실패는 허용된 오류 분류로 표현한다.
- 공개 카탈로그의 newsletter_name만 표시용으로 허용한다. 사용자 닉네임·기사 제목·선택 문장에서 이름을 추출하지 않는다.
- 계측 실패가 로그인·구독·열람을 막지 않는다. 기존 수집 선택과 인증 상태를 존중한다.

## 수용 조건 (Acceptance Criteria)

- [x] AC-01: 모든 활성 지표에 산식·단위·기간·중복·제외·이벤트·제공 위치가 있다.
- [x] AC-02: 모든 활성 필드가 현재 지표·진단에 대응하고 전역 ID·동의어 ID·대기 이벤트가 생성되지 않는다.
- [x] AC-03: 온보딩·가입 단계는 screen_view의 step_key로 측정하며 같은 노출을 별도 단계 이벤트로 중복 기록하지 않는다.
- [x] AC-04: 인증 성공은 login, 그 외 인증 종료는 auth_attempt_finished로 분리한다. 가입·프로필·건너뛰기는 별도다.
- [x] AC-05: 목록 노출은 content_state_viewed의 ready로 측정하며 홈의 빈 상태·오류·안내 선택을 구분한다.
- [x] AC-06: 기사 선택·본문 표시·30초 열람을 구분하며 배경·비가시·로딩 시간은 제외한다.
- [ ] AC-07: 재평가·복귀·취소·응답 역전·계정 변경에서 중복·잘못된 결과가 발생하지 않는다.
- [x] AC-08: 가입 추천의 직접 구독도 기록하고, unknown 상태·팝업 로드·복귀를 신규 구독 완료로 바꾸지 않는다.
- [x] AC-09: 검색·목록은 하나의 list_view_id를 쓰고 기사·뉴스레터·구독의 필요한 수명만 별도 식별한다.
- [x] AC-10: 허용 타입·조건부 필드·정보 범위·SDK 한도를 검사한다. 현재 최대 키 수는 13개다.
- [ ] AC-11: 개발/상용 연결·자동 수집·제외 방식과 대상 버전·수집 시작일을 확인한다.
- [ ] AC-12: GA4 개요와 정확한 원시 집계를 구분하고 미측정·미성숙·분모 0을 다르게 표시한다.
- [ ] AC-13: 가짜 시계·기록기로 결정적 테스트, 적용 범위의 전체 테스트·Release 빌드·개발 DebugView 검증을 남긴다.
- [ ] AC-14: 새 지표·필드 추가 예시에서 기존 계약 호환과 버전 전환을 검증한다.
- [ ] AC-15: 화면·기능 이용과 뉴스레터별 상세/독자/빈도/구독 시도/저장 보고서에 사용자 수·횟수·분모를 구분한다.
- [x] AC-16: 북마크·하이라이트는 저장 성공 후 기록하며 실패·취소·중복 응답·선택 원문은 포함하지 않는다.
- [ ] AC-17: 뉴스레터 ID로 집계하고 이름 변경·동명이름·라벨 누락에도 합산/분리 오류가 없으며 미계측 기능을 0으로 표시하지 않는다.
- [ ] AC-18: M06·M08은 정해진 24시간 관찰 완료 집단만 확정 집계하며 미성숙 성공도 같은 기준으로 제외한다.
- [ ] AC-19: 동일 timestamp의 SDK 이벤트 순서·기간용 시각을 실제 원시 표본으로 검증하고 경로·단계 의미가 다른 비율을 같은 품질 지표로 해석하지 않는다.

표시·결과 경계의 구현 및 로컬 테스트를 통과한 수용 조건만 체크한다. AC-07의 전체 실제 UI 경로와 AC-11·AC-13의 SDK 수신/운영 시작, 보고서·원시 export 조건은 별도 확인이 남는다.

설계 분석 결과와 수정·보류 근거는 [review.md](review.md)에 기록한다. 문서 계약 검증은 실제 SDK 수집 검증을 대신하지 않는다.
