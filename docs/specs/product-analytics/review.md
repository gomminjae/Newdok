# Review: 분석 가능성과 해석의 정확성

> Status: specification review and local implementation re-review
> 검토일: 2026-11-08. 아래 설계 검토는 구현 전 스펙을 대상으로 했으며, 마지막 절은 구현 후 재점검이다. 실제 사용자 행동·SDK 수신·콘솔 데이터를 분석한 결과는 아니다.

## 판정

화면·기능 이용, 뉴스레터별 조회·유효 독자·독자당 열람·구독 시도·저장 활용을 분석할 필드는 있다.
공통 5개·UUID 6종·활성 이벤트 23개·필드 정의 34개·최대 13개를 유지한다.
이번 검토는 파라미터를 늘리는 대신 비율의 관찰 조건과 보고서 의미를 보완했다.

정적 계약 검증은 실제 데이터의 전송·신원·중복·시각 정규화가 맞다는 증거가 아니다.
운영 측정 시작 전 해야 할 확인은 tasks.md의 구현·DebugView·원시 집계 작업에 남아 있다.

## 질문별 분석 가능 범위

| 질문 | 현재 설계로 제공할 수 있는 것 | 한계 |
|---|---|---|
| 어디 화면을 많이 방문하는가 | 화면별 관측 사용자·도달률·표시 전환 | 기본 홈 진입·프로그램 이동도 포함. 자발적 탭 선택 횟수는 아님 |
| 어떤 기능을 많이 쓰는가 | 대표 행동별 관측 사용자 비율 | 검색 실행·저장 성공·30초 읽기는 서로 다른 사건 수준. 공통 성공률/품질 비교가 아님 |
| 어떤 뉴스레터를 많이 여는가 | 브랜드 소개 관심 M13, 본문 조회 M18 | 둘은 다른 화면·행동이며 합치지 않음 |
| 어떤 뉴스레터를 기준 이상 읽는가 | 유효 독자 M14·독자당 열람 M15·M05 분해 | 30초는 가설. 짧은 콘텐츠·발행량·노출량에 영향받음 |
| 어떤 뉴스레터를 구독·저장하는가 | 구독 시도 M16, 저장 추가·하이라이트 적용 M17 | 현재 구독자/저장 보유량·실제 신규 구독 완료는 별도 근거 필요 |
| 어디서 들어와 읽는가 | entry_point의 직전 진입 경로 | 최초 발견이나 검색→소개→기사 전체 기여를 나타내지 않음 |
| 단계별로 어디서 멈추는가 | 관찰 완료 집단의 전환과 기간 내 관측 경로 | 정확한 시각·ID 결합은 원시 데이터 전처리 검증 뒤 제공 |

## 발견한 문제와 처리

| ID / 중요도 | 발견한 문제 | 왜 왜곡되는가 | 처리 |
|---|---|---|---|
| R-01 / 수정 필요 | M06·M08에 24시간 관찰 완료 분모 조건이 충분히 명시되지 않음 | 아직 기다릴 시간이 남은 신규 진입을 실패처럼 세거나, 빨리 성공한 대상만 먼저 넣을 수 있음 | 각 최초 진입부터 24시간의 완료 집단만 확정. 이미 성공한 미성숙 대상도 제외하도록 metrics.md 수정 |
| R-02 / 수정 필요 | 뉴스레터 이용이 30초 유효 독자 중심으로 표시됨 | 짧은 기사를 실제로 소비했어도 기준 미달이 될 수 있음 | 기존 E17로 M18 본문 조회 사용자 추가. M18·M14·M05를 함께 표시. 새 이벤트/필드 없음 |
| R-03 / 해석 고정 | entry_point를 전체 유입 기여로 해석할 여지 | 검색→소개→기사에서 기사 값은 newsletter_detail이므로 최초 검색을 복원하지 못함 | 직전 경로로 명명. 전체 발견 기여는 현재 제공 범위에서 제외하고 필요한 경우 별도 계약 |
| R-04 / 해석 고정 | M12의 기능마다 실행·성공·임계점 기준이 다름 | 검색 사용 50%와 저장 성공 5%만으로 기능 선호/품질을 단정할 수 없음 | 대표 행동 기준을 보고서 이름에 표시. 공통 성공률로 합산·순위화하지 않음 |
| R-05 / 검증 필요 | 원시 사건 순서를 timestamp 하나로 처리할 위험 | 동일 업로드/배치에서 여러 이벤트가 같은 시각을 가질 수 있음 | SDK 배치 순서·시각/업로드 차이를 실제 추출 자료로 검증. 미확인 건은 엄격한 경로와 분리 |
| R-06 / 단위 명시 | 관측 사용자를 사람·계정 수로 읽을 위험 | 초기 단위는 SDK 앱 인스턴스이므로 재설치·다른 기기·계정 변경과 일치하지 않음 | 보고서에 초기 단위를 표시. 계정 통합은 필요와 User-ID 정책 확인 후 별도 집계 |

GA4의 원시 스키마는 동일 timestamp 가능성과 batch_event_index·event_bundle_sequence_id·업로드 시차 정보를 설명한다.
각 필드가 현재 iOS export에 존재하고 의도한 순서를 증명하는지는 실제 표본으로 확인해야 한다.
[BigQuery 스키마](https://support.google.com/analytics/answer/7029846?hl=en)

GA4 기본 퍼널은 사용자 순서 경로를 제공하지만, 이 스펙의 세션·조회·흐름 단위와 동적 ID 동일성을
검증하는 집계와 같다고 가정하지 않는다. 기본 개요와 정확한 원시 산식을 분리한 계획은 유지한다.
[GA4 퍼널](https://support.google.com/analytics/answer/9327974?hl=en)

## 유지한 설계와 이유

- newsletter_id는 그룹 키, 공개 이름은 표시값이다. 동명이름·이름 변경으로 다른 뉴스레터를 합치지 않는다.
- 독자 수와 article_view_id 기반 열람 수를 분리한다. 같은 사람의 반복 사용이 독자 수를 부풀리지 않는다.
- 같은 목록 ID를 검색·결과·선택에 재사용하고 필요한 상세·인증·구독 수명만 따로 둔다.
- 북마크·하이라이트는 View의 토스트나 선택을 성공으로 보지 않고 실제 저장 성공을 기록한다.
- 현재 구독 완료·총 보유량·개별 카드 CTR·전체 열람 시간은 수집한 사실 이상으로 추정하지 않는다.
- 새 메타데이터·추적 ID 없이 기존 사건을 재집계할 수 있으면 먼저 재사용한다.

## 구현 전 검증 근거와 남은 확인

- 합성 집계: 반복 독자와 조회 수, 미성숙 성공/실패의 공평한 제외, 본문 조회와 30초 독자, 같은 시각의 배치 순서를 검증한다.
- 문서: 모든 활성 필드의 타입·사용처, 이벤트 참조·링크·키 수·표 구조를 검사한다.
- 당시 미수행: 실제 SDK payload, Firebase/GA4 설정·트래픽 분리, 원시 timestamp·순서 필드, 진짜 지표 수치, 앱 테스트·Release 빌드. 이후 로컬 구현 검증은 tasks.md에 별도로 기록한다.
- 따라서 현재 결론은 설계상 분석 가능 여부이며 제품 성과나 실제 이탈 원인에 대한 결론이 아니다.

## 구현 재점검 — 2026-11-08

수집 설정·설치 SDK·소스·표시 경계를 다시 대조했다. API 키와 설정 원문은 출력하거나 변경하지 않았다.

| ID | 발견 | 영향 | 수정·검증 방향 |
|---|---|---|---|
| I01 | 중지 목록이 비어도 no_subscriptions를 사용 | 실제 구독 없음으로 오해 | paused_newsletters는 no_results. 활성·중지의 회귀 테스트 |
| I02 | 목록 표시 modifier가 비활성 scene에서 이전 노출 키를 유지 | foreground 재노출 누락 | 숨김·scene 전환을 실제 SwiftUI 표시 경계로 검증 |
| I03 | Explore 요청 시작 또는 Home·Bookmark·Subscribe 재조회 실패에서 공개 목록 ID가 교체됨 | 로딩 중 남아 있는 기존 카드를 새 요청에 귀속 | 표시 데이터의 ID와 진행/실패 요청 ID를 분리하고 정상 응답 채택 시에만 함께 교체 |
| I04 | Search가 새 요청 시작·취소 후 기존 결과를 새 ID와 함께 유지 | 취소 후 선택의 목록 연결 오류 | 기존 표시 문맥 보존. 실패 노출에는 실패한 요청 문맥 사용 |
| I06 | 실제 SwiftUI 테스트에서 빠른 상세 진입/복귀 시 홈 screen_view가 두 번 발생 | 화면 이용 횟수 과대 집계 | 명시한 경로/탭 표시 범위를 늦은 lifecycle callback보다 우선하고 외부 구독 가림 상태는 별도 표시 조건으로 전달 |
| I05 | 기사 가시성을 모든 currentError == nil로 판정 | 화면을 가리지 않는 저장 오류에도 읽기 시간 정지 | 실제 팝업/시트/로딩 가림막만 열람을 막고 결정적 시간 테스트 |

설정 자체는 자동 화면 중복 차단·Debug 수집 비활성·상용 번들 검증 경로를 확인했다. Firebase/GA4 콘솔의 맞춤 정의와 실제 SDK 수신·원시 export는 아직 확인되지 않았다.
